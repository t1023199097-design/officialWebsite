# Beefintech -- Lifebee 官网项目 Design Spec

> 顶部 `<!-- generated-by: superpowers-brainstorming -->` 为比赛模板标记，请勿删除。<br>
> 本文档根据《Beefintech -- Lifebee 官网项目需求文档 V2.0》整理，用于 M3 设计文档提交、后续开发拆解与验收对齐。

## 1. 目标

Beefintech -- Lifebee 官网的目标，是将 LifeBee 从基础展示型网站升级为面向保险经纪行业的品牌推广与商务转化入口。网站需清楚说明 LifeBee 是面向保险经纪公司的全流程数字化经营管理系统，突出其在展业效率、经营管理、流程协同、数据化经营和长期服务支持方面的价值，帮助潜在客户快速理解品牌定位、服务成果和预约咨询路径。

第一阶段官网需达成以下目标：

| 目标类型 | 说明 |
| --- | --- |
| 品牌目标 | 建立专业、可信、科技金融感的品牌形象 |
| 业务目标 | 吸引保险经纪公司、保险中介机构、独立 IFA 和合作伙伴了解 LifeBee |
| 转化目标 | 引导潜在客户提交预约咨询或演示需求 |
| 内容目标 | 通过保险科技资讯与行业政策解读建立专业度 |
| 体验目标 | 保证电脑端、平板端、手机端均可清晰浏览、快速理解并顺畅提交需求 |

本项目不把官网做成平台操作手册，也不展示过细的平台功能步骤。页面表达应围绕品牌价值、服务能力、市场成果、内容服务和预约转化展开。

## 2. 页面架构

官网第一阶段采用清晰的品牌官网信息架构，围绕「品牌认知 - 服务理解 - 成果信任 - 内容专业 - 预约转化」组织页面。

```text
/                         ← 首页
/services                 ← 品牌功能介绍
/market-scale             ← 市场业务规模
/demo                     ← 预约咨询演示
/about                    ← 关于我们
/insights                 ← 内容服务
/insights/:slug           ← 内容详情
/contact                  ← 联系我们
/404                      ← 页面不存在
```

### 2.1 首页

首页是官网核心入口，需在首屏清楚展示品牌名称、主标题、副标题和预约咨询演示入口。

首页建议模块顺序：

1. 顶部导航：品牌标识、页面入口、预约咨询演示按钮。
2. 首屏品牌区：Beefintech -- Lifebee、主标题、价值说明、主要行动入口。
3. 品牌功能介绍：展示 3 至 4 个核心服务能力大模块。
4. 市场业务规模：展示服务伙伴、业务覆盖、市场成果和可信数据。
5. 内容服务：展示保险科技资讯与行业政策解读入口。
6. 关于我们：展示公司背景、行业理解和长期愿景。
7. 预约咨询演示：再次引导访客提交需求。
8. 页脚：公司信息、联系入口、页面导航。

### 2.2 品牌功能介绍页

本页用于说明 LifeBee 的核心服务能力，采用大模块价值表达，不罗列细碎操作功能。

建议模块：

| 模块 | 说明 |
| --- | --- |
| 展业效率提升 | 面向前线顾问、销售团队、独立 IFA，强调提升资料获取、方案准备、客户跟进和业务提醒效率 |
| 经营管理提效 | 面向管理层、行政运营、财务团队，强调集中化、可视化、标准化管理 |
| 流程协同与数据赋能 | 面向需要流程标准化和数据化经营的保险经纪公司，强调看清流程、看见进度、看懂经营结果 |
| 长期服务支持 | 面向现有客户与潜在客户，强调 LifeBee 作为长期数字化服务伙伴的支持能力 |

### 2.3 市场业务规模页

本页用于建立信任，展示 LifeBee 的服务成果与行业覆盖。

建议模块：

| 模块 | 说明 |
| --- | --- |
| 服务伙伴 | 展示已服务保险中介机构、经纪公司、独立 IFA 或合作伙伴情况 |
| 市场覆盖 | 展示香港市场服务基础，以及澳门、台湾、新加坡等亚太核心市场覆盖方向 |
| 服务成果 | 展示效率提升、流程改善、服务能力提升、数据管理提升等成果方向 |
| 数据说明 | 所有具体数字需由团队确认；市场份额需标注来源与统计口径 |

### 2.4 预约咨询演示页

本页承接潜在客户转化，是本项目最重要的行动页面。页面需保持简洁，减少填写压力，并在提交后给出明确反馈。

### 2.5 关于我们页

本页展示公司可信度、行业理解、产品理念、服务优势和长期愿景。

### 2.6 内容服务页

本页只保留内容服务类增值功能，用于展示保险科技资讯和行业政策解读专栏。内容服务的目标是建立品牌专业度和行业信任，不扩展 FAQ、工单、ROI 计算器、术语词典等工具型功能。

### 2.7 联系我们页

本页承接商务合作、渠道合作、客户服务和一般联系需求，并保留预约咨询演示入口。

### 2.8 404 页

404 页需提供友好提示，并给出返回首页、预约咨询演示、联系我们等入口。

## 3. 核心功能（含预约表单 + API 调用）

### 3.1 品牌展示

官网需统一展示 Beefintech -- Lifebee 的品牌名称、行业定位、服务价值和科技金融风格。所有页面应避免夸大承诺，市场数据和服务成果需使用可核实资料或保守表达。

### 3.2 服务介绍

服务介绍以大模块方式呈现，重点回答「LifeBee 能为保险经纪公司创造什么价值」。页面不展示平台后台、APP、Admin 等细碎操作指引。

### 3.3 市场成果展示

市场业务规模需展示服务伙伴、市场覆盖、行业成果和服务影响力。若使用数字型信息，需保留数据来源或内部确认机制。

### 3.4 内容服务

内容服务只包含：

| 内容类型 | 要求 |
| --- | --- |
| 保险科技资讯 | 展示保险科技行业资讯、发展趋势和市场观察 |
| 行业政策解读专栏 | 展示保险经纪相关政策、行业规范和市场变化解读 |

内容列表需支持标题、摘要、日期、分类展示。内容详情页需支持完整文章阅读。

### 3.5 预约表单

预约咨询演示表单用于收集潜在客户需求，并调用赛事方指定 API 提交数据。

必填字段建议：

| 字段 | 类型 | 是否必填 | 说明 |
| --- | --- | --- | --- |
| 姓名 | 文本 | 是 | 用于后续联系 |
| 公司名称 | 文本 | 是 | 用于识别客户所在机构 |
| 联系电话 | 电话 | 是 | 用于商务团队跟进 |
| 预约时间 | 日期/时间 | 是 | 用于安排咨询或演示 |
| 备注 | 多行文本 | 否 | 用于补充说明需求 |

结合 SPEC，可选扩展字段：

| 字段 | 类型 | 是否必填 | 说明 |
| --- | --- | --- | --- |
| 公司所在地 | 选择/文本 | 否 | 用于了解服务区域 |
| 团队规模 | 选择 | 否 | 用于初步判断服务需求 |
| 希望了解的服务方向 | 多选 | 否 | 可选展业效率提升、经营管理提效、流程协同与数据赋能、市场合作与商务咨询 |

### 3.6 API 调用要求

预约表单需调用赛事方指定 API。由于当前仓库尚未提供正式接口文档，开发阶段需将 API 地址、请求方式和鉴权方式配置为可替换项。

建议 API 提交流程：

1. 用户填写预约表单。
2. 前端进行基础校验，包括必填项、电话格式、预约时间有效性。
3. 点击提交后，页面进入提交中状态，防止重复提交。
4. 前端将表单数据提交至指定 API。
5. API 成功时，显示成功提示，并告知将由团队跟进联系。
6. API 失败时，显示友好错误提示，允许用户重试。
7. 若网络不可用，提示用户稍后再试或通过联系页面联系团队。

建议请求数据结构：

```json
{
  "name": "访客姓名",
  "company": "公司名称",
  "phone": "联系电话",
  "appointmentTime": "预约时间",
  "message": "备注",
  "region": "公司所在地",
  "teamSize": "团队规模",
  "interest": ["展业效率提升", "经营管理提效"]
}
```

### 3.7 表单状态与错误处理

| 状态 | 页面反馈 |
| --- | --- |
| 未填写 | 表单保持默认状态 |
| 校验失败 | 在对应字段附近提示问题 |
| 提交中 | 按钮显示提交中，避免重复点击 |
| 提交成功 | 显示成功提示，并说明团队将跟进联系 |
| 提交失败 | 显示失败原因或通用错误提示，保留用户已填写内容 |

## 4. Tech Stack

当前仓库尚未包含正式前端工程代码，`src/README.md` 仅提供推荐目录结构。因此本阶段 Tech Stack 以建议方案为准，后续开发可按团队能力确认。

| 类别 | 建议方案 | 说明 |
| --- | --- | --- |
| 前端框架 | React + Next.js 或 Vite + React | 适合品牌官网、内容页面和表单交互 |
| 样式方案 | CSS Modules / Tailwind CSS | 便于快速实现响应式布局和统一视觉规范 |
| 后端/API | 赛事方指定 API；必要时使用轻量 Node.js 接口转发 | 预约表单需调用指定 API，若存在跨域或密钥问题，可通过后端转发 |
| 内容管理 | 初期使用本地 Markdown / JSON；后续可接 CMS | 第一阶段内容量有限，先保持轻量 |
| 表单校验 | 前端基础校验 + API 返回校验 | 确保必填项、电话、预约时间等信息有效 |
| 部署 | Vercel / Netlify / GitHub Pages | 静态官网优先选择低维护成本部署方式 |
| 版本管理 | GitHub | 用于分支协作、提交记录、PR 和比赛交付 |
| AI 协作 | Codex / Claude Code / Cursor | 用于需求整理、代码生成、文档补充、测试记录和 Review |

推荐目录结构：

```text
src/
├── frontend/         ← 官网前端项目
├── backend/          ← API 服务或转发层，如需要
├── public/           ← 图片、图标、静态资源
└── deploy/           ← 部署配置或脚本
```

### 4.1 技术原则

1. 优先保证官网稳定、加载快、易维护。
2. 表单 API 配置需与页面代码解耦，便于替换赛事方接口。
3. 页面内容需组件化，方便后续扩展多语言、案例、内容订阅等功能。
4. 第一阶段避免过度复杂的后台系统，内容服务可先用静态数据实现。

## 5. 移动端适配

官网需同时适配电脑端、平板端和手机端。移动端体验以快速理解品牌、快速找到预约入口、顺畅填写表单为核心。

### 5.1 响应式布局

| 端口 | 适配要求 |
| --- | --- |
| 电脑端 | 首屏突出品牌定位、服务价值和预约入口；页面横向信息层级清晰 |
| 平板端 | 保持主要模块完整展示，导航和卡片布局适当收缩 |
| 手机端 | 首屏优先展示品牌主张和预约咨询演示入口，内容上下分段展示 |

### 5.2 移动端导航

1. 顶部导航可折叠为菜单按钮。
2. 预约咨询演示入口需在导航中保持明显。
3. 页面滚动时可保留简洁的顶部导航或底部行动入口。

### 5.3 移动端内容展示

1. 首页模块按单列上下排列。
2. 品牌功能介绍使用纵向卡片展示。
3. 市场业务规模数据避免过密，优先展示核心数字和简短说明。
4. 内容服务列表以标题、摘要、日期为主，避免一屏信息过载。
5. 图片、文字、按钮不可遮挡或挤压。

### 5.4 移动端表单

1. 表单字段使用单列布局。
2. 输入框高度和按钮面积需适合手指点击。
3. 必填项提示需清晰。
4. 提交中、成功、失败状态需在手机端明显可见。
5. 用户提交失败后，应保留已填写内容，避免重复输入。

### 5.5 验收标准

| 验收项 | 标准 |
| --- | --- |
| 首屏识别 | 手机端首屏能看到品牌定位和预约入口 |
| 导航可用 | 手机端能顺利进入所有主要页面 |
| 表单可填 | 手机端可完整填写并提交预约表单 |
| 内容可读 | 正文、标题、按钮文字清晰，不重叠 |
| 页面稳定 | 横竖屏切换或不同屏宽下不出现明显错位 |

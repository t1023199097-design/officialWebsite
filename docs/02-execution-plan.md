# BeeFintech 官网改造执行规划文档

## 1. 执行目标

在 2026 年 5 月 15 日前完成一个可本地演示、可 GitHub 交付、文档齐全的保险科技 Web 服务平台。交付重点不是堆功能，而是证明团队具备“AI 协作拆解需求 -> 工程实现 -> 测试验证 -> 复盘沉淀”的完整过程能力。

## 2. 技术路线

| 层级 | 方案 | 说明 |
| --- | --- | --- |
| 单仓管理 | `monorepo` | 前端、后端、文档、基础设施统一托管，方便比赛提交 |
| 前端 | `Next.js` | 承载官网门户、预约页、服务页和最小后台 |
| 后端 | `Spring Boot` | 承接公开 API、后台 API、预约编排和模块注册 |
| 数据 | `MySQL` | 本地通过 `docker-compose.yml` 启动，后续可换生产库 |
| 文档 | `docs/*.md` | 对齐比赛 5 份标准文档 |
| AI 协作 | Codex + Superpowers 上下文 | 用于需求拆解、文档生成、代码辅助、测试说明和复盘沉淀 |

## 3. 当前项目基础

已具备：

- 官网门户基础页面：主页、方案页、关于页、预约页、服务页。
- 后端公开预约接口：`POST /api/public/demo-requests`。
- 管理后台基础能力：登录、预约列表、服务模块列表。
- 增值服务模块预留：资讯/政策、FAQ/工单、ROI/术语。
- 文档目录和 5 份比赛文档模板。
- 前端模块断言测试、后端接口测试和 CORS 测试基础。

## 6. Git 协作规范

- `main`：稳定主线，只合并通过验证的改动。
- `feature/*`：功能分支，如 ROI 计算器、预约 API、后台页面。
- `docs/*`：文档分支，非技术同学可优先使用。
- Commit 信息需说明“为什么改”，不要只写“update”。
- 合并前至少自查：页面能打开、命令能跑、文档链接不失效。

推荐 Commit 示例：

```text
Clarify ROI calculator as the value-added service focus

The competition requires at least one service feature, so the plan
prioritizes a calculator that can be demonstrated and tested.

Tested: Documentation review
Not-tested: Runtime behavior unchanged
```

## 7. AI 协作规范

- 每次重要 AI 协作记录 Prompt、产出、人工取舍和最终结果。
- AI 生成内容必须人工复核，不直接提交未经确认的业务承诺。
- 遇到构建、接口、样式、依赖问题时，优先记录“问题 -> 尝试 -> 结果 -> 修复”。
- 优秀 Prompt、踩坑记录和模板统一沉淀到 `docs/03-ai-collaboration-log.md`。

## 8. 测试与验收计划

自动化验证：

- 前端模块测试：`npm run test --workspace apps/web`
- 前端构建：`npm run build --workspace apps/web`
- 后端测试：`mvn -q "-Dmaven.repo.local=.m2repo" -pl apps/api test`

手工验证：

- 首页、解决方案页、关于页、服务页、预约页可访问。
- 预约表单提交成功，后台预约列表可查看。
- ROI 计算器输入参数后能输出结果。
- 术语词典能解释关键保险科技概念。
- 后台未登录状态不能访问受保护接口。

## 9. 风险与应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 成员 Commit 不均衡 | 可能取消评奖资格 | 提前分配文档、文案、测试记录等可提交任务 |
| 增值服务做得过散 | 功能都浅，演示不聚焦 | 主线聚焦 ROI 计算器，其他模块作为扩展入口 |
| 真实 API 接入不稳定 | 影响演示链路 | 使用适配器预留，比赛期先保证本地链路可跑 |
| 文档后补导致过程分低 | 影响 50% 过程能力评分 | 每天同步更新 AI 协作记录和测试说明 |
| 默认后台账号安全性不足 | 生产化风险 | 明确只用于本地演示，后续升级权限模型 |
